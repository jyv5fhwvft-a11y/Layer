Layer 4 defines the reusable functional systems that make the Interactive Knowledge Lexicon work consistently across its pages. It connects the learner experience, concept-page structure and authoritative content through shared mechanisms.

Central principle: Build the shared mechanism once. Reuse it across concepts. Keep each component independent. Keep the learning content authoritative.

1. Purpose and Objectives

Layer 1 defines the learner experience. Layer 2 defines how individual concept pages are structured and presented. Layer 3 defines how educational content and its supporting data are organised.

Layer 4 defines the shared mechanisms that make those experiences function.

For example, quizzes on the Ping and Process pages should use the same underlying assessment system. Their questions and answers differ, but the mechanism that displays questions, checks answers, calculates scores and provides feedback is reusable.

The objectives are to:

  • Avoid rebuilding the same functionality for every concept.
  • Provide consistent learning interactions.
  • Make shared features easier to maintain.
  • Allow new concepts to use existing functionality.
  • Keep educational content separate from functional code.
  • Prevent one malfunctioning component from unnecessarily disabling an entire concept page.
  • Support future expansion without rebuilding the platform.

2. Scope of Layer 4

Layer 4 covers the reusable functional systems used across IKL:

  1. Shared navigation and page services.
  2. Search and concept discovery functionality.
  3. Quiz and assessment mechanisms.
  4. Interactive simulations.
  5. Diagrams and visual learning mechanisms.
  6. Calculations and interactive problem-solving.
  7. Learning progress and completion tracking.
  8. Revision and knowledge reinforcement.
  9. Shared glossary and references.
  10. Accessibility and interaction support.
  11. Cross-feature communication and reusable services.
  12. Error handling and independent component operation.

Layer 4 does not redefine the educational structure of a concept page or the content schema established in Layer 3. It provides the functional mechanisms that operate with those structures.

3. Core Architectural Principle

One shared learning system, many independent concepts

Every concept should be able to use the same collection of reusable functional mechanisms.

Concept Educational Content Shared Functionality
Ping Networking explanations Quiz, simulation, progress
Process Operating system explanations Quiz, simulation, progress
API Software development explanations Quiz, interactive example, progress
Encryption Cybersecurity explanations Quiz, simulation, progress

The concept supplies its own educational material and configuration. The shared system interprets that information and provides the appropriate interaction.

Separation of responsibilities

  • Content: What the learner is taught.
  • Presentation: How the learner sees the information.
  • Functionality: How the learner interacts with it.

This separation makes the platform reusable and easier to maintain.

4. Shared Navigation and Page Services

IKL requires consistent navigation between its pages and learning features.

Shared navigation mechanisms should support:

  • Returning to the homepage.
  • Moving between concept sections.
  • Moving to related concepts.
  • Opening prerequisite concepts.
  • Navigating between learning categories.
  • Returning to a previous learning position where supported.
  • Providing consistent navigation controls across concept pages.

Navigation should respect the concept relationships defined in Layer 3. The shared navigation system provides the mechanism; the concept registry provides the relevant destination information.

5. Search and Concept Discovery

The search mechanism should provide a consistent way to find concepts throughout IKL. It should use the central concept registry established in Layer 3.

Expected capabilities include:

  • Searching by concept name.
  • Searching by recognised alternative terms.
  • Searching by relevant keywords.
  • Displaying matching concepts.
  • Showing category information.
  • Opening the correct concept page.
  • Respecting publication status.
  • Avoiding links to unpublished or unavailable concepts.

Search should not maintain an independent, conflicting list of concepts. The central registry remains the authoritative source for concept identity and publication information.

6. Shared Quiz and Assessment Engine

The assessment engine provides reusable mechanisms for testing learner understanding. Individual concepts supply their own questions, answers, explanations and assessment configuration. The shared engine handles the interaction.

Expected capabilities

  • Displaying questions and answer choices.
  • Accepting learner responses.
  • Checking answers.
  • Providing immediate feedback.
  • Explaining why an answer is correct or incorrect.
  • Calculating scores where appropriate.
  • Displaying completion results.
  • Supporting different question formats.
  • Recording assessment completion where permitted.
  • Supporting retry and revision.

Possible question formats

  • Multiple-choice questions.
  • True-or-false questions.
  • Matching exercises.
  • Ordering or sequencing exercises.
  • Short-answer questions.
  • Scenario-based questions.
  • Practical problem-solving questions.

The architecture should allow additional question formats to be introduced without rebuilding every concept page.

Educational feedback

Assessment should teach, not merely judge.

For an incorrect answer, the engine should be capable of displaying the correct answer, explaining why it is correct, explaining why the selected answer was incorrect, and identifying which concept explanation the learner should revisit.

The assessment mechanism is shared, but the educational feedback is supplied by the relevant concept content.

7. Shared Interactive Simulation Engine

Simulations allow learners to experiment with an educational concept rather than only read about it. The shared simulation mechanism should provide reusable interaction capabilities.

Expected capabilities

  • Accepting learner input.
  • Responding to user actions.
  • Updating visual states.
  • Displaying the result of an action.
  • Allowing the learner to reset an experiment.
  • Providing instructions and explanations.
  • Supporting different simulation types.
  • Handling invalid inputs safely.

Examples

  • Ping simulation: A learner selects a destination device and observes whether a simulated connection succeeds or fails.
  • Operating system process simulation: A learner observes how processes compete for CPU time.
  • Virtual memory simulation: A learner explores how logical addresses are translated into physical memory locations.
  • Encryption simulation: A learner observes how a simplified encryption example transforms readable information.

These are examples of how the shared simulation mechanism could be used. They are not instructions to implement these simulations immediately.

A simulation should operate as an independent component. If it fails, the surrounding educational explanation and other working page features should remain available wherever technically possible.

8. Shared Diagram and Visual Learning Mechanism

IKL uses diagrams to make technical concepts easier to understand. Layer 4 provides reusable mechanisms for presenting and interacting with diagrams.

Supported visual formats

  • Static diagrams.
  • Flowcharts.
  • Sequence diagrams.
  • Process diagrams.
  • Component diagrams.
  • Relationship diagrams.
  • Step-by-step visual explanations.
  • Interactive diagrams.

Expected capabilities

  • Displaying diagrams consistently.
  • Supporting diagrams supplied by concept content.
  • Providing labels and explanations.
  • Supporting zoom or enlargement where appropriate.
  • Highlighting selected components.
  • Showing relationships between components.
  • Supporting step-by-step visual sequences.

The architecture may use SVG, Mermaid or other appropriate visual technologies. The precise rendering technology can be selected during implementation without changing the educational responsibility of this layer.

9. Shared Calculation and Problem-Solving Mechanisms

Some concepts require learners to enter values and observe calculated results. IKL should support reusable calculation mechanisms.

Examples

  • Binary and decimal conversion.
  • Memory address calculations.
  • Page-number and offset calculations.
  • Network-related calculations.
  • Algorithmic problem-solving exercises.

Expected capabilities

  • Accepting learner inputs.
  • Validating input formats.
  • Performing the configured calculation.
  • Displaying results.
  • Explaining the calculation steps.
  • Showing appropriate error messages.
  • Allowing learners to try again.

The calculation mechanism should be reusable. Individual concepts provide the relevant formulas, parameters, instructions and educational explanations.

10. Shared Learning Progress Mechanism

Layer 1 establishes the learner experience and the importance of learning continuity. Layer 4 provides the reusable mechanisms that support it.

Potential progress information

  • Sections viewed or completed.
  • Assessments attempted.
  • Assessment completion.
  • Simulation completion where applicable.
  • Concept completion.
  • Revision activity.
  • Learning milestones.

Expected capabilities

  • Recording supported learning events.
  • Calculating completion states.
  • Displaying progress indicators.
  • Restoring progress where persistence is available.
  • Communicating progress to other learner-facing features.
  • Supporting appropriate privacy and data controls.
Important distinction: Viewing a page does not necessarily mean that the learner understands it. Progress indicators should distinguish content viewed, activity attempted, assessment completed and concept marked as completed. The system must not automatically claim mastery simply because a learner opened a page.

11. Shared Revision and Knowledge Reinforcement

IKL should provide reusable mechanisms for helping learners revisit previously studied material.

Expected capabilities

  • Revisiting important explanations.
  • Reattempting assessments.
  • Displaying revision questions.
  • Highlighting important terms.
  • Connecting revision activities to relevant concepts.
  • Supporting quick-revision material.
  • Connecting prerequisite and related concepts.

The revision mechanism should be capable of using the Quick Revision section defined in Layer 2. The educational content remains owned by the concept; the shared mechanism provides the means to revisit it.

12. Shared Glossary and References

Technical concepts frequently introduce unfamiliar terminology and external sources. IKL should provide shared mechanisms for accessing this supporting knowledge.

Glossary functionality

  • Displaying definitions of technical terms.
  • Linking terms to relevant concepts.
  • Supporting consistent terminology across pages.
  • Providing contextual explanations where appropriate.

Reference functionality

  • Displaying references associated with a concept.
  • Providing source titles and relevant links.
  • Supporting consistent reference presentation.
  • Keeping reference information separate from page-rendering code.

The shared glossary and references established in Layer 3 remain the authoritative supporting resources. Layer 4 provides the mechanisms for displaying and accessing them.

13. Accessibility and Interaction Support

Shared functionality must support an accessible learning experience.

  • Keyboard accessibility where supported.
  • Screen-reader-friendly interaction.
  • Clear labels for controls.
  • Understandable feedback messages.
  • Sufficient visual contrast.
  • Visible focus indicators.
  • Alternatives to interactions that depend exclusively on colour.
  • Clear instructions for simulations and assessments.
  • Appropriate touch interaction on mobile and tablet devices.

Accessibility should be considered within each reusable component rather than added as an afterthought to individual concepts.

14. Cross-Feature Services and Communication

IKL contains several features that need to communicate with one another.

For example:

  • Completing a quiz may update learning progress.
  • Completing a concept may affect a learner's learning record.
  • Opening a prerequisite may connect to concept navigation.
  • A glossary term may link to a concept page.
  • A revision activity may be connected to an earlier assessment.

Layer 4 should provide consistent ways for shared components to communicate.

Expected architectural principles

  • Clear interfaces between components.
  • Predictable data exchange.
  • Reusable event or notification mechanisms where appropriate.
  • Avoiding unnecessary dependencies between components.
  • Avoiding duplicated functionality.
  • Keeping responsibilities clearly separated.

A component should not need to know the internal implementation details of every other component it communicates with.

15. Modular Components and Independent Failure

A central requirement of Layer 4 is that reusable components should operate as independently as reasonably possible.

For example, if the quiz component fails:

  • The concept explanation should remain accessible.
  • The glossary should continue to work.
  • Navigation should remain available.
  • An unrelated simulation should not automatically stop working.

If a diagram cannot load, the surrounding educational explanation should remain available and an appropriate error or alternative presentation should be shown where possible.

Expected safeguards

  • Independent component initialisation.
  • Input validation.
  • Graceful error handling.
  • Clear error messages.
  • Protection against one component unnecessarily disabling another.
  • Appropriate fallback behaviour.
  • Diagnostic information for later investigation.

This principle does not mean every failure can be isolated completely. It means the architecture should minimise unnecessary failure propagation.

16. Technical Architecture and Implementation Considerations

Layer 4 defines functional responsibilities rather than locking the project into an unapproved implementation.

The existing project uses HTML, CSS and JavaScript. The architecture should favour reusable JavaScript modules and shared components compatible with the existing GitHub Pages environment.

Possible functional modules

  • Navigation service.
  • Search service.
  • Assessment engine.
  • Simulation engine.
  • Diagram renderer.
  • Calculation engine.
  • Progress service.
  • Revision service.
  • Glossary and reference service.
  • Accessibility utilities.
  • Shared error-handling mechanisms.

These are conceptual module responsibilities, not a final approved file or folder structure.

Technology principles

  • Prefer simple, maintainable solutions.
  • Reuse existing project capabilities where appropriate.
  • Avoid unnecessary frameworks or infrastructure.
  • Keep content separate from functional code.
  • Avoid making a backend mandatory without a demonstrated requirement.
  • Consider iPad-compatible development and testing workflows.
  • Preserve the existing working website.

Any specific library, framework, storage mechanism or service should be evaluated before implementation.

17. Quality Assurance and Testing Requirements

Shared functionality must be tested independently and as part of the complete learning experience.

Functional testing

  • Does each component perform its intended function?
  • Does the quiz engine check answers correctly?
  • Do simulations respond appropriately?
  • Do calculations produce correct results?
  • Does progress update correctly?
  • Do glossary and reference links work?

Integration testing

  • Does Layer 4 work with Layer 2's concept-page structure?
  • Does it correctly interpret Layer 3 content and configuration?
  • Does search use the central concept registry?
  • Does assessment completion communicate with progress?
  • Do concept relationships support navigation?

Failure testing

  • What happens when a component cannot load?
  • What happens when required data is missing?
  • What happens when a learner enters invalid information?
  • Can unrelated features continue operating?

Device and accessibility testing

  • Does the functionality work on an iPad?
  • Are touch controls usable?
  • Are instructions understandable?
  • Can supported interactions be accessed without a mouse?
  • Are errors and results communicated clearly?

No component should be considered complete merely because it appears on the screen. Its behaviour must also be tested.

18. Relationship with the Five IKL Layers

Layer 1 — Learner Experience
Defines what learners should be able to experience and accomplish.
Layer 2 — Concept Page and Template
Defines how concept information and learning activities are structured and presented.
Layer 3 — Content and Data
Defines the authoritative educational content, concept registry, relationships and supporting knowledge resources.
Layer 4 — Shared Functionality
Provides the reusable mechanisms that make the learning activities and shared features work.
Layer 5 — Quality, Automation and Publishing
Defines the quality controls, validation workflows, deployment, monitoring, backup and recovery processes.

How the layers work together

A concept's educational content is defined in Layer 3. Layer 2 provides its page structure. Layer 4 supplies the reusable functionality required by that page. Layer 1 defines the learner-facing experience. Layer 5 governs the quality and controlled publication of the finished system.

19. Implementation Boundaries and Approval Record

This document defines the architecture for Layer 4. It does not authorise immediate implementation.

Project protection rules
  • No repository restructuring.
  • No file renaming or moving.
  • No replacement of existing working pages.
  • No modification of the existing Ping page.
  • No creation of new shared engines in GitHub.
  • No adoption of a new framework or backend without evaluation and approval.
  • No automatic publication that bypasses human approval.
The existing GitHub Pages site must remain intact while the architecture is being reviewed.

Required approval sequence

  1. Complete the normal-text Layer 4 architecture document.
  2. Review its contents.
  3. Make any requested corrections.
  4. Obtain explicit approval.
  5. Create the matching HTML architecture document.
  6. Add the approved HTML document to GitHub.
  7. Verify that it opens correctly.
  8. Proceed to Layer 5.

Final Architectural Principle

The purpose of Layer 4 is to make IKL a reusable learning platform rather than a collection of individually constructed educational pages.

A new concept should be able to use the shared learning mechanisms without requiring those mechanisms to be rebuilt.

Build the shared mechanism once. Reuse it across concepts. Keep each component independent. Keep the learning content authoritative.
