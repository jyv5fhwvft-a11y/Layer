Document Purpose

What This Document Establishes

This document establishes the complete learner-facing experience of the Interactive Knowledge Lexicon (IKL). It defines what learners should be able to discover, understand, practise, achieve and experience while using the Lexicon.

It consolidates the original 126 approved Layer 1 decisions and the clarifications reviewed during consolidation.

Core distinction: Layer 1 defines what the learner should experience. The creator's technical learning explains how we design, build, test, maintain and teach the system that makes that experience possible.
Two Connected Learning Journeys

1. The Learner and the Creator

Journey A — The IKL Learner

Students use the Lexicon to discover technical concepts, learn at an appropriate level, explore explanations and examples, interact with diagrams and simulations, assess understanding, track learning, develop skills, prepare for careers and complete practical projects.

Journey B — Learn as You Create / Learn as You Build

The creator learns how to design, develop, maintain and teach the technology behind the Lexicon.

  • HTML — page structure.
  • CSS — visual presentation.
  • JavaScript — rendering, interactions and functionality.
  • JSON — structured educational content and concept data.
  • Reusable templates and components.
  • Simulations, diagrams and assessment engines.
  • GitHub, version control and publishing.
  • Automation, testing and software architecture.

The creator's learning is part of the wider project. It is not excluded simply because Layer 1 concentrates on the student's experience.

Project Architecture

2. The Five Layers

The layers work together. A learner may experience all five simultaneously, although each has a different development responsibility.

Layer 1 — Learner Experience What learners see, access, do and experience.
Layer 2 — Concept Page and Template The reusable structure and presentation of concept pages.
Layer 3 — Content and Data Educational material and structured concept information.
Layer 4 — Shared Functionality Reusable tools and engines for quizzes, simulations, diagrams and interactions.
Layer 5 — Quality, Automation and Publishing Validation, review, approval, deployment, monitoring and backups.
Approved hybrid direction: HTML provides page structure, CSS provides visual design, JavaScript provides rendering and functionality, and JSON provides structured educational content and concept data. Detailed implementation belongs in the appropriate technical architecture and creator-learning documents.
Part I · Original Decisions 1–24

3. Homepage, Discovery and Navigation

The homepage must provide an accessible starting point from which learners can discover concepts, explore categories and navigate the Lexicon.

Ten Homepage Areas

  1. Welcome section.
  2. Search section.
  3. Category discovery.
  4. Featured concepts.
  5. Guided learning pathways.
  6. Recently visited concepts.
  7. Recommended concepts.
  8. Knowledge Map introduction.
  9. About the Lexicon.
  10. Footer.

Discovery and Navigation Requirements

  • Search by concept names, technical terms, keywords, aliases and abbreviations.
  • Support natural-language descriptions, suggestions and helpful search results.
  • Provide clear handling of unsuccessful searches.
  • Support category discovery, initially including Computer Networking, Operating Systems, Programming, Software Development, Cybersecurity, Databases and Computer Architecture.
  • Show featured concepts, guided pathways, recently visited concepts and related recommendations.
  • Support independent exploration without forcing a fixed learning sequence.
  • Provide a Knowledge Map discovery experience.
  • Keep navigation, terminology and presentation consistent.
  • Support responsive devices, accessibility and privacy-conscious local search history.

Discovery principle: Learners should find what they need without having to understand the internal organisation of the website.

Part II · Original Decisions 25–49

4. Reading, Understanding and Accessing Concepts

  • Explore concepts using categories and combined filters.
  • Receive relevant search suggestions with category information.
  • Navigate through the complete concept lesson using a table of contents covering all 15 official sections.
  • See the current section, visited sections and resume reading position.
  • Understand estimated reading time.
  • Adjust text size, line spacing and visual theme without losing educational content.
  • Use optional text-to-speech and speech highlighting.
  • Access downloadable or printable educational material and complete lesson PDFs where appropriate.
  • Understand that website-based simulations and interactive features may not be reproducible as static PDF content.
  • Access concepts through dedicated, shareable URLs.
  • See concept identity, category, title, subtitle and learning information.
  • Understand learning objectives and expected outcomes as separate items.
  • Identify essential and recommended prerequisites.
  • Understand lesson difficulty separately from explanation level.
  • Use optional knowledge checks and assessments.
  • Access consistent terminology and explanations across supported languages.
Important: Opening or visiting a section does not automatically mean that the learner has mastered it. The system distinguishes opening, visiting, completing an activity and demonstrating knowledge.
Part III · Original Decisions 50–58

5. Progressive and Personalised Learning

Four explanation levels are established:

  1. Very simple / first-grader level.
  2. Beginner level.
  3. Undergraduate level.
  4. Technical / advanced level.

Learners should be able to move between levels and revisit explanations. Learning resources may include simple explanations, analogies, mental models, technical explanations, practical examples, diagrams, interactive simulations, knowledge checks, assessments and explanations of mistakes or misconceptions.

Recommendations may reflect learning activity and stated preferences. Optional confidence ratings must not be treated as objective proof of competence. Self-assessment must remain distinguishable from observed activity and demonstrated performance.

Principle: Personalisation should be understandable, optional and learner-controlled.

Part IV · Original Decisions 59–79

6. Goals, Learning Records, Portfolios and Skills

  • Personal learning goals, examples, calendar and milestones.
  • Optional learning streaks and achievement badges.
  • Personal learning records and progress indicators.
  • A private Learning Portfolio containing concepts, activities, assessments, projects and evidence.
  • Screenshots, demonstrations, external project links and PDF export where appropriate.
  • Optional sharing with learner-controlled privacy and visibility settings.
  • Skills summaries and evidence-linked skill categories.

Skill Development Stages

  1. Introduced.
  2. Developing.
  3. Practised.
  4. Demonstrated.

The system should explain why a skill has been assigned a particular stage and recommend further development. It must distinguish studying a subject, practising a skill and demonstrating a skill.

Streaks must not erase achievements or punish learners for taking a break. Certificates are non-accredited completion records unless a separate recognised accreditation arrangement exists. Private portfolio information remains private unless the learner chooses to share it.

Part V · Original Decisions 80–91

7. Career Development and Employment Readiness

The initial approved career catalogue contains 18 distinct pathways:

  1. Software Developer
  2. Network Engineer
  3. Cybersecurity Analyst
  4. Systems Administrator
  5. Database Administrator
  6. Cloud Engineer
  7. Prompt Engineer
  8. UI/UX Designer
  9. Ethical Hacker
  10. Cyber Forensics Expert
  11. Cyber Crime Digital Expert
  12. Kali Linux Instructor
  13. Ethical Hacking Expert
  14. Geopolitics Expert / Geopolitical Analyst
  15. Victim Profiler
  16. Suspect Profiler
  17. Deepfake Expert
  18. Deepfake Application Designer

Distinct approved career titles must remain distinct. Ethical Hacker and Ethical Hacking Expert; Cyber Forensics Expert and Cyber Crime Digital Expert; Deepfake Expert and Deepfake Application Designer; Victim Profiler and Suspect Profiler are separate entries.

Responsible Professional Practice

  • Profiling content must be evidence-based, acknowledge uncertainty and avoid unsupported behavioural assumptions.
  • Cybersecurity learning must emphasise lawful, authorised and ethical practice.
  • Deepfake analysis must address synthetic-media detection, authenticity assessment and digital forensics.
  • Deepfake application design must address responsible creation, detection, verification and management.

Career Development Experience

  • Foundation, Intermediate and Advanced stages.
  • Career-specific skills and learning requirements.
  • Essential and recommended prerequisites.
  • Specialist branches and career comparisons.
  • Optional career exploration without forced recommendations.
  • Optional readiness assessments that never prevent beginners from starting at Foundation.
  • Readiness reports covering strengths, gaps, starting level, prerequisites, learning sequence, projects and milestones.
  • Online reports, PDF export and optional private Learning Portfolio storage.
  • Dated, sourced and periodically reviewed employment-market information.
  • Current job listings with source, posting information and application links when available.
  • Transparent job-readiness gap analysis.
Market trends, salary information and job listings are not guaranteed outcomes. Completing IKL content must not be presented as a guarantee of employment.
Part VI · Original Decisions 92–103

8. Interview Preparation and Technical Challenges

Interview Modes

  1. Guided Practice.
  2. Mock Interview.
  3. Timed Interview.

Interview preparation includes reusable career- and subject-based question banks, model answers, evaluation criteria, explanations, practice history, previous answers, feedback and progress comparisons.

Optional spoken-answer recording and transcription require microphone permission. Learners control recording retention and deletion. Communication coaching must distinguish measurable speech patterns from subjective impressions.

Six Individually Visible Evaluation Dimensions

  1. Technical accuracy.
  2. Completeness.
  3. Clarity and communication.
  4. Problem-solving approach.
  5. Practical reasoning.
  6. Professional presentation.

Scores must include understandable explanations and transparent criteria. Interview preparation includes the STAR method: Situation, Task, Action and Result.

Technical Challenges

Challenges should be available across relevant career pathways and include Guided, Simulation-based and Independent modes, with hints, solutions, explanations, feedback, scoring, attempt history and repeat attempts.

Security-related exercises must use authorised, controlled environments and promote lawful professional practice.

Part VII · Original Decisions 104–109

9. Technical Projects and Practical Experience

  • Create and manage projects with descriptions and objectives.
  • Record progress, development stages and evidence.
  • Connect projects to career pathways and skills.
  • Maintain a development history.
  • Use career-specific templates, including software development, networking, cybersecurity, databases, cloud and UI/UX.
  • Work through Beginner, Intermediate and Advanced project levels.
  • Receive evaluation and useful feedback.
  • Showcase selected work with screenshots, demonstrations, technologies, skills and external links.
  • Export appropriate project information.
  • Choose whether projects remain private or are shared.
  • Collaborate where supported, with participation and contribution controls.

Project evaluation should consider knowledge, implementation, problem-solving, completeness and quality. Feedback must explain how learners can improve, not merely provide a score.

Project evidence may contribute to skills records and portfolios. Private project storage must remain distinct from optional public showcasing.

Part VIII · Original Decisions 110–119

10. Mentoring

  • Mentor profiles and verification of credentials and experience.
  • Clear distinction between verified information and unverified claims.
  • Mentor discovery, matching, invitations and acceptance.
  • Scheduling and private messaging.
  • Project annotations and feedback.
  • Mentor dashboards, learning goals and action plans.
  • Progress reviews and feedback on learner development.

Mentoring communication and private information must be protected. Learners should be able to understand a mentor's relevant experience and expertise before deciding whether to engage.

Part IX · Original Decisions 120–126

11. Learner Support, Help and Community

  • Searchable Help Centre and Frequently Asked Questions.
  • Beginner-friendly onboarding, navigation guidance and feature explanations.
  • Problem reporting.
  • Personalised dashboard showing current activities, goals, progress, recent projects, assessments, career development, recommendations and notifications.
  • Unified notifications for reminders, goals, milestones, mentor invitations and messages, collaboration updates, assessment feedback and announcements.
  • Learner-controlled notification preferences; notifications should be useful and non-intrusive.
  • Data export and deletion controls, privacy settings, portfolio visibility, data-retention information and recording controls.
  • Optional moderated learning community.

The community must have appropriate moderation, reporting, privacy protections and clear standards against harassment and abuse. Community contributions must not automatically become approved educational content.

Learners retain meaningful control over personal information, sharing and participation.

Cross-feature Requirements

12. Shared Learner Experience Principles

Learner Control

Learners should understand and control optional features, personalisation, sharing, notifications and privacy settings.

Private by Default

Personal learning records, portfolios, project information and mentoring communications should be private unless the learner chooses otherwise.

Explainable Progress

The Lexicon must distinguish visits, study, practice, assessment and demonstrated ability.

Evidence-Based Skills

Skill descriptions and proficiency stages should connect to appropriate evidence. Self-reports, automated evaluations and human feedback must remain distinguishable.

Accessible Learning

The experience should support different devices, learning needs and levels of technical understanding.

Responsible Educational Practice

Career, cybersecurity, profiling and synthetic-media content must be handled responsibly and with appropriate professional safeguards.

Human Review

Learner reports and feedback must be reviewed appropriately. User submissions must not directly change published educational content.

Consistency

Navigation, terminology, feedback, visual language and learner controls should be consistent throughout the Lexicon.

Brand and Presentation

13. Visual Identity and Presentation

  • Deep navy and blue as the principal identity.
  • White and soft-light reading backgrounds.
  • Electric blue for actions and interactive controls.
  • Teal for progress and success.
  • Amber for notes and warnings.
  • Rounded cards and subtle shadows.
  • Clear, readable typography and consistent spacing.

The Lexicon should retain a recognisable identity across its homepage, concept pages, learning tools and supporting areas.

Protection and Access

14. Privacy, Security and Learner Protection

Privacy and learner control are foundational requirements, not optional decorative features.

  • Private-by-default personal learning information.
  • Appropriate protection of accounts and personal information where accounts are introduced.
  • Learner-controlled sharing.
  • Clear data export and deletion options.
  • Appropriate handling of recordings and microphone permissions.
  • Protected mentoring communications.
  • Moderated community participation.
  • Transparent recommendations and progress information.
  • Clear distinctions between observed activity, self-reported information, automated evaluation and human feedback.

Features should collect and retain only information necessary for their intended purpose.

Accessibility and Device Support

The Lexicon must be designed for responsive use across mobile phones, tablets including iPad, laptops and desktop computers. The experience should support readable text, suitable contrast, accessible controls, clear labels, text alternatives, keyboard access and screen-reader compatibility.

Educational content should remain understandable when a learner cannot use a particular visual or interactive feature.

Scope and Authority

15. Layer Boundaries and Implementation Authority

Approval of this document establishes the learner-facing requirements for Layer 1.

It does not, by itself:

  • Authorise changes to GitHub.
  • Authorise a website migration.
  • Approve every technical architecture proposal.
  • Approve implementation of every feature.
  • Declare that all proposed features have already been built.
  • Remove the need for testing and quality review.

Layers 2–5 retain their respective responsibilities. Technical decisions must be documented in the appropriate architecture and technical reference materials. Implementation must follow the project's approval and publishing process.
