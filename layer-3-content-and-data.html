01Purpose and Objectives

Layer 3 defines how the educational knowledge inside the Interactive Knowledge Lexicon is stored, identified, organised, connected and maintained.

It establishes a structured content system so that every concept can be managed consistently and presented through the reusable architecture defined in Layer 2.

Primary objectives

  • Establish one authoritative data source for each concept.
  • Give every concept a permanent identity.
  • Maintain a central registry of all concepts.
  • Represent relationships between concepts consistently.
  • Separate shared educational resources from individual concepts.
  • Distinguish content versions from schema versions.
  • Validate content before publication.
  • Separate educational information from application code.
Core principle: IKL must have a reliable source of truth for its knowledge. A concept's content should not be scattered across multiple page files or duplicated in unrelated parts of the application.

02Scope of Layer 3

Layer 3 governs the structure and management of educational content and its supporting data.

Included responsibilities

  • Individual concept data files.
  • Central concept registry.
  • Permanent concept identifiers and slugs.
  • Concept categories and publication status.
  • Concept relationships.
  • Shared glossary, references and common examples.
  • Content schema and content versioning.
  • Completeness and structural validation.
  • Selective component configuration.

Outside the scope of this layer

  • Learner-experience strategy, governed by Layer 1.
  • Concept-page presentation, governed by Layer 2.
  • Shared application behaviour, governed by Layer 4.
  • Testing automation and publishing processes, governed by Layer 5.

04Authoritative Concept JSON

Each concept must have an individual structured JSON record. This record is the authoritative source for that concept's educational content and declared presentation configuration.

Why individual concept files?

  • Concepts can be created and maintained independently.
  • Content changes do not require rewriting the page template.
  • Validation can be performed concept by concept.
  • Concepts can be reused in different parts of IKL.
  • Content remains separate from application code.

Illustrative concept record

{
  "id": "IKL-NET-0001",
  "name": "Ping",
  "slug": "ping",
  "category": "Computer Networking",
  "contentVersion": "1.0.0",
  "schemaVersion": "1.0",
  "publicationStatus": "published",

  "sections": {
    "conceptIdentity": {},
    "firstGraderExplanation": {},
    "analogy": {},
    "beginnerExplanation": {},
    "technicalExplanation": {},
    "componentsArchitecture": {},
    "workingMechanism": {},
    "interactiveSimulation": {},
    "flowchartSequence": {},
    "practicalExample": {},
    "misconceptions": {},
    "limitationsTroubleshooting": {},
    "conceptConnections": {},
    "knowledgeAssessment": {},
    "quickRevision": {}
  }
}
This is an illustrative structural example, not a completed production schema. Exact field definitions, data types and validation rules belong in the formal schema specification.

05The Central Concept Registry

IKL must maintain a central registry that acts as the authoritative index of its concepts.

The registry allows the application to discover concepts without searching through individual page files manually.

Required registry information

Field Purpose
Permanent ID Uniquely identifies a concept over time.
Name Provides the learner-facing concept name.
Slug Provides a stable URL-friendly identifier.
Category Places the concept within a subject area.
Publication status Identifies whether the concept is a draft, review item or published entry.
Content path Locates the authoritative concept data file.
Content version Identifies the version of the educational content.

What the registry powers

  • Homepage concept discovery.
  • Category listings.
  • Search results.
  • Concept navigation.
  • Related-concept discovery.
  • Publication monitoring.
Important distinction: The registry tells IKL which concepts exist and where their content is located. It does not replace the detailed educational content inside each concept record.

06Permanent Concept Identity

Every concept must receive a permanent identifier that remains stable even if its display name, category or URL-friendly slug changes.

Identity principles

  • Every concept has one unique permanent ID.
  • Permanent IDs must not be reused for another concept.
  • Display names may change without changing the permanent ID.
  • Slugs must be managed consistently.
  • References between concepts should use permanent IDs.

Illustrative identity

Permanent ID: IKL-NET-0001
Name: Ping
Slug: ping
Category: Computer Networking

The permanent ID is the concept's identity. The name and slug are descriptive identifiers that may be updated under controlled rules.

07The Approved 15-Section Content Schema

Each concept's educational content follows the approved teaching structure established in Layer 2.

  1. Concept Identity and Definition
  2. First-Grader Explanation
  3. Analogy and Mental Model
  4. Beginner Explanation
  5. Technical Explanation
  6. Components and Architecture
  7. Working Mechanism
  8. Interactive Simulation
  9. Flowchart and Sequence Diagram
  10. Practical Example
  11. Common Mistakes and Misconceptions
  12. Limitations and Troubleshooting
  13. Connections to Other Concepts
  14. Knowledge Assessment
  15. Quick Revision

Schema principles

  • Every concept uses the same overall section model.
  • Each section has a defined purpose and expected data structure.
  • Section content is adapted to the subject being taught.
  • Required and optional fields are explicitly distinguished.
  • Missing required information must be detectable through validation.
A consistent schema does not mean identical content. Ping, Process and Encryption should follow the same teaching structure while using their own relevant examples, diagrams and simulations.

08Concept Relationships

IKL must represent relationships between concepts through four defined relationship types.

Prerequisite A concept the learner should understand before studying another.
Related A concept that shares a meaningful subject or connection.
Contrast A concept that helps explain differences between ideas.
Application A concept that demonstrates where or how another concept is used.

Relationship rules

  • Relationships must refer to valid permanent concept IDs.
  • Each relationship must have one of the four approved types.
  • Broken or unknown references must be detected.
  • Relationships should have a meaningful educational purpose.
  • Prerequisite relationships should support a sensible learning progression.

Illustrative relationship record

{
  "conceptId": "IKL-NET-0001",
  "relationships": [
    {
      "type": "prerequisite",
      "targetId": "IKL-NET-0002"
    },
    {
      "type": "related",
      "targetId": "IKL-NET-0003"
    },
    {
      "type": "contrast",
      "targetId": "IKL-NET-0004"
    },
    {
      "type": "application",
      "targetId": "IKL-NET-0005"
    }
  ]
}

The IDs above are illustrative. They do not assert that these particular concept relationships have been established.

09Shared Knowledge Resources

Some educational information is useful across multiple concepts. Such information should not need to be duplicated independently in every concept file.

Three shared resource groups

  • Shared glossary: reusable definitions of technical terms.
  • Shared references: sources used to support and verify educational content.
  • Common examples: reusable practical examples where appropriate.

Shared-resource principles

  • Shared resources should have identifiable records.
  • Concepts should reference shared resources rather than copy them unnecessarily.
  • Shared content must be maintained consistently.
  • References must be traceable to the content they support.
  • Concept-specific explanations should remain in the concept record.
Shared resources reduce duplication. They do not prevent a concept from explaining a term in its own educational context.

10Content and Schema Versioning

IKL must distinguish between two different kinds of change: changes to educational content and changes to the structure used to organise that content.

Version type What it represents Example
Content version Changes to the information or teaching material of a concept. Ping explanation improved from 1.0.0 to 1.1.0.
Schema version Changes to the structure or rules of concept data. A new required field is introduced into the concept schema.

Versioning principles

  • Content version and schema version must be stored separately.
  • A content edit must not automatically imply a schema change.
  • A schema change must be identifiable independently.
  • Compatibility and migration requirements must be considered when schemas change.
  • Version information must be available for validation and maintenance.
Why this matters: IKL must be able to improve the explanation of Ping without confusing that edit with a change to the structure used by every concept.

11Publication Status

Every concept must have an explicit publication status. The application must not assume that every concept record is ready for public learning.

Publication-status principles

  • A concept's status must be recorded in the registry.
  • Publication status must be distinguishable from content version.
  • Draft content must not be mistaken for approved public content.
  • Publication must depend on the required quality checks.
  • Search and discovery must respect the concept's publication status.

Illustrative status values

draft
in_review
published
archived

These labels illustrate a possible status vocabulary. The exact transition rules and permissions belong in the detailed governance and publishing specifications.

12Content and Configuration

Concept content and application code must remain separate. JSON records describe educational information and may selectively declare which supported components a concept uses.

Responsibilities

  • JSON stores structured concept information.
  • JSON may declare supported component configuration.
  • Application code interprets those declarations.
  • Component engines determine how declared components behave.
  • Concept content must not contain executable application logic.

Illustrative component configuration

{
  "componentConfiguration": {
    "interactiveSimulation": {
      "enabled": true,
      "componentType": "network-ping-simulation"
    },
    "flowchart": {
      "enabled": true,
      "format": "mermaid"
    }
  }
}
A configuration declaration does not create the component engine. The application must already support the declared component type and validate its configuration.

13Validation and Completeness

Structured content must be checked before it is treated as ready for publication. Validation protects IKL from incomplete, inconsistent or disconnected knowledge records.

Required validation areas

Schema validation Checks that concept data follows the required structure.
Completeness checks Detects missing required sections or information.
Registry checks Confirms registry entries point to valid concept records.
Relationship checks Detects broken or unknown concept references.
Resource checks Detects missing shared glossary entries and references.
Publication checks Confirms required conditions are met before publication.

Examples of errors to detect

  • A registry entry points to a missing JSON file.
  • Two concepts accidentally use the same permanent ID.
  • A concept is missing a required teaching section.
  • A relationship points to a concept that does not exist.
  • A declared component type is unsupported.
  • A required shared resource cannot be found.
  • A published concept fails its required validation rules.
Publication principle: The existence of a JSON file is not proof that a concept is complete. Completeness and validity must be checked explicitly.

14Relationship with Page Rendering

Layer 3 supplies structured information. Layer 2 determines how that information is presented to learners.

Separation of responsibilities

  • Layer 3 maintains the authoritative concept content.
  • Layer 2 defines the concept page and teaching presentation.
  • Layer 4 supplies shared functionality used by the application.
  • Rendered pages display the content but do not become its authoritative source.

Authoritative data flow

Authoritative Concept JSON
          |
          v
     Data Validation
          |
          v
  Concept Page Renderer
          |
          v
    Generated HTML
          |
          v
   Learner Experience
Critical rule: Generated HTML is output, not the authoritative content source. If a generated page needs correction, the authoritative data and relevant rendering logic must be corrected rather than treating the generated HTML as the master record.

16Quality and Governance

Content governance ensures that the knowledge base remains reliable as the number of concepts grows.

Governance principles

  • Every concept has a permanent identity.
  • Every concept has one authoritative content record.
  • Changes are reflected in the appropriate version.
  • Relationships are traceable and valid.
  • Shared resources are maintained consistently.
  • Publication status is explicit.
  • Validation results inform publication readiness.
  • Content changes should not silently break existing concepts.

Long-term maintainability

The architecture must support the addition of many concepts without requiring a separate page implementation for every new topic. It must also support controlled improvements to existing content and the schema itself.

17Relationship Between the Five Layers

Layer Responsibility Relationship to Layer 3
Layer 1 Learner Experience Defines what the learner should be able to discover and experience.
Layer 2 Concept Page and Template Consumes structured content and presents it through reusable pages.
Layer 3 Content and Data Maintains authoritative knowledge and its relationships.
Layer 4 Shared Functionality Provides shared behaviour that reads and uses the data.
Layer 5 Quality, Automation and Publishing Validates and supports reliable delivery of content and application changes.

Layer 3 is the knowledge foundation. It ensures that the information presented by IKL has a consistent structure, identifiable source and maintainable relationships.

18Implementation Boundaries

Approval of the Layer 3 architecture establishes the governing content and data direction. It does not automatically authorise changes to the existing GitHub repository.

Implementation controls

  • Do not restructure existing files without approval.
  • Do not migrate current concept content without approval.
  • Do not replace working HTML pages without approval.
  • Do not introduce a new data framework without approval.
  • Do not treat illustrative JSON examples as production files.
  • Explain the purpose and consequences of each implementation step.
  • Preserve working functionality while planning improvements.
Architecture approval and implementation authorisation are separate decisions. The approved architecture guides future work; it does not grant automatic permission to alter the live repository.
